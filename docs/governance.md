# ナレッジ検索AI 運用ガバナンス手順書

対象システム: 案件7 ナレッジ検索AI（Slack連携RAGシステム）
最終更新: 2026-08-08

## 1. 目的

本書は、ナレッジ検索AIが保持する文書のアクセス権限・機密区分を適切に管理し、部署別アクセス制御の実効性を維持するための運用手順を定める。特に、文書の機密区分（機密度）が変更された場合の対応フローを明確化する。

## 2. 用語・現状のデータモデル

- **部署（department）**: 文書が属する部署（戦略/業務/IT/人事/営業/管理）。検索時のアクセス制御の主軸。`case7.slack_users`で1ユーザーにつき1部署のみ登録できる（複数部署の兼任は現状未対応）。
- **機密度（confidentiality）**: 文書ごとに記録される区分。現状は取り込み文書全てが「社外秘」。M&A関連等、より高い機密区分の文書が今後追加される可能性がある。
- **クエリログ（query_logs）**: 誰が・いつ・何を質問し・どのチャンク（文書内のセクション単位）が参照されたかを記録する監査ログ（`case7.query_logs`）。**このログは追記専用（append-only）として扱い、事後に内容を書き換えない**（第4.4節参照）。

## 3. 【重要】現状のシステム制約

現時点の実装では、**検索時のアクセス制御は「部署」のみで行っており、「機密度」カラムは記録されているだけでアクセス制御には反映されていない**。つまり、ある文書の機密度を「社外秘」から「厳秘」に変更しても、システムの挙動（誰が検索でヒットさせられるか）はそれだけでは変わらない。

機密度を実際のアクセス制御に反映させるには、以下のいずれかのシステム改修が別途必要になる。

- 機密度が高い文書を、特定の役職・担当者のみに閲覧を絞る仕組み（`case7.slack_users`に「複数部署の兼任」または「manager/特別権限フラグ」を追加する等。現状は1ユーザー1部署のため、特定個人だけに機密文書を見せる用途にはスキーマ拡張が必要）
- 機密度が高い文書は、通常の部署別検索の対象から除外し、別途申請制のアクセス経路を設ける

このため、Phase 1（現行運用）における機密度変更は、**システム上のアクセス制御の変更ではなく、次章の「部署の変更（`department`を`機密`にする）」による運用対応**を基本とする。機密度に応じた自動的なアクセス制御が必要になった時点で、上記のシステム改修を実施すること。

## 4. 機密扱い変更時の対応フロー

### 4.1 トリガーとなる典型的な事象

- M&A案件のクローズ・契約終了により、関係者限定の情報から社内共有可能な情報に変わる（機密度が下がる）
- 進行中の重要案件（M&A、大型契約、人事に関わる調査等）に関する文書が新たに機密指定される（機密度が上がる）
- 顧客からの要請、法務・コンプライアンス部門の指示による機密区分の見直し

### 4.2 機密扱いへの変更（一時除外）フロー

| ステップ | 担当 | 内容 |
|---|---|---|
| 1. 申請 | 文書の所管部署の担当者 | 対象文書・変更理由・希望する新しい機密区分をナレッジ管理者に連絡する |
| 2. 判断 | ナレッジ管理者（情報システム部門） | 対象文書を検索対象から一時除外するかを即時判断する |
| 3. 一時対応 | ナレッジ管理者 | `case7.documents.department`を**`機密`という固定値**に変更する（部署名の運用ルールとして統一する。`機密`部署に所属するSlackユーザーは存在しないため、実質的に誰の検索にもヒットしなくなる）。第3章の制約により、`confidentiality`カラムの変更だけでは検索結果から除外されない点に注意 |
| 4. 恒久対応 | ナレッジ管理者 + 開発担当 | 継続的な個別アクセス制御（特定の役職者にだけ見せる等）が必要と判断された場合は、第3章に記載のシステム改修の要否を検討し、対応する |
| 5. 記録 | ナレッジ管理者 | 変更日・変更理由・対応内容を台帳（別途Excel等で管理、または将来的に`case7.documents`に変更履歴カラムを追加）に記録する |
| 6. 事後確認 | ナレッジ管理者 | `case7.query_logs`を確認し、機密度変更前に当該文書のチャンクへアクセスしたユーザー・質問内容を洗い出す（変更前のアクセスに問題がなかったかの事後点検に使う） |

### 4.3 完全に削除したい場合のフロー

| ステップ | 担当 | 内容 |
|---|---|---|
| 1. 検索インデックスからの削除 | ナレッジ管理者 | `case7.documents`から対象レコードを削除する（`case7.chunks`はON DELETE CASCADEで連動して削除される） |
| 2. **SharePoint上の元ファイルも削除** | ナレッジ管理者 | **必須。省略不可**。SharePoint月次同期（`app/api/cron/sharepoint-sync`）は「最終更新日時」のみを見て新規・更新ファイルを取り込む設計であり、削除の追跡は行わない。検索インデックス側だけ削除してSharePoint側にファイルを残すと、後日誰かがそのファイルに触れて更新日時が変わった瞬間に**同期ジョブが再度取り込み、削除したはずの文書が復活する**。 |
| 3. 記録 | ナレッジ管理者 | 削除日・削除理由を台帳に記録する |

### 4.4 監査ログ（query_logs）の扱いについて【重要】

文書やチャンクを削除しても、**`case7.query_logs.retrieved_chunk_ids`に記録された過去のチャンクIDは削除・redactしない**。理由は以下の通り。

- クエリログの目的は「機密度変更前に誰が何を見たか」を事後的に検証できることであり（4.2節ステップ6）、ログ自体を書き換えるとこの検証機能が失われる
- 削除済みチャンクへの参照は「参照先が既に存在しない」状態としてそのまま残ればよく、レポート作成時は`case7.chunks`とのJOINが空になる形で自然に表現される
- 個人情報保護等の理由でログの消去が本当に必要な場合は、本節のような日常的な文書削除フローとは別に、法務部門を交えた個別のデータ消去プロセスとして扱う

### 4.5 緊急時対応（誤って機密文書が広く検索可能だった場合）

1. 発見次第、ナレッジ管理者は当該文書を`case7.documents`から即時削除する（4.3節の手順に従い、SharePoint側の削除も忘れない）
2. `case7.query_logs`で、誤公開期間中に当該文書のチャンクにアクセスしたユーザーと質問内容を特定する
3. 情報システム部門・法務部門へ報告し、影響範囲に応じて追加対応（アクセスしたユーザーへの注意喚起、顧客への報告要否の判断等）を行う

## 5. 定期監査

- **月次利用レポートを自動配信済み**（`app/api/cron/monthly-audit-report`、毎月1日にVercel Cronで自動実行）。部署別の質問件数・利用者数・「該当なし」回答件数を集計し、統括Slackチャンネルへ投稿する。ナレッジ管理者はこのレポートで、想定外の部署からの機密文書への問い合わせ（本来ブロックされるはずが漏れていないか）がないかを確認する。
  - 現状は部署管理者ごとの個別配信ではなく、統括チャンネルへの一括投稿。個別配信が必要な場合は`case7.slack_users`への「部署管理者」フラグ追加が前提となる（第6章参照）。
- 四半期ごとに`case7.documents`の機密度設定を棚卸しし、実態と乖離がないか確認する

## 6. 今後の拡張（Phase 2候補）

- 役職別アクセス制御・複数部署兼任対応（現行は1ユーザー1部署のみ）
- 機密度に応じた自動アクセス制御（第3章参照）
- `case7.documents`への変更履歴カラム追加（誰がいつ機密度を変更したかをシステム内で追跡できるようにする）
- 月次レポートの部署管理者ごとの個別配信（`case7.slack_users`への管理者フラグ追加が前提）
